## How to read this file

Every section heading starts with one of four labels, so the tally is
mechanical and an entry can never be quietly promoted from open to fixed:

- `## Fix: ` — the defect is fixed, and the entry carries the evidence.
- `## Left unfixed: ` — still present in the tree, with what is known and
  what would settle it.
- `## Declared limit: ` — present and accepted: a trade the module makes on
  purpose, not pending work. Carries the reason it is accepted.
- `## Not a defect: ` — investigated and found to be the kernel's rule, the
  test program's bug, or a misreading, with the control that proves it.

`## Superseded: ` is a fifth label and is deliberately **not** in the tally. It
marks a decision record whose status is carried by another entry, so that the
fix is counted once, in the entry that holds the measurement. Two headings in
this file have changed label under an archivist pass and both were defects of
the *bookkeeping*, not of the tree:

- "a data page is only ever traced once, not once per handler epoch" read
  `## Fixed:`, which no tool recognises, so a real fix sat in no column at all.
  It is now `## Superseded:` and the fix is counted at "A data page read through
  a second handler version is not traced again".
- "the fault-path swallow is a fixed point, not a convergence" read
  `## Open, model only:`, also unrecognised. Its own body ends "Left open", so
  the tally was reporting **0 left unfixed** while this file carried an entry
  that says in prose it is unsettled and that the shipped check is narrower than
  its own comment claims. It is now `## Left unfixed:`, which is the honest
  column, and "(model only, never measured on a kernel)" is in the heading
  because nothing on a kernel settles it.

## Fix: `exact=1` did not apply to `comm`

`pb_is_target` still used `strstr` on `current->comm`. `exact=1` only affected the exec pathname check, so a shorter token still tracked the process.

Fix: the comm check calls `pb_name_matches`. The suite loads `path=extr exact=1` and requires `extra epoch` to miss, then `path=extra exact=1` to pass.

## Fix: A data read was logged on every fault

`pb_handle_data` appended `ip data_va epoch` after every swallowed read. If the page had already been dumped for that handler epoch, `epoch` was 0.

Fix: append one line, and only after a successful dump. The epoch is the handler epoch. `extra read` still passes.

## Fix: `data=` stopped after the first armed page

The first successful `PROT_NONE` set a process-wide flag. A page mapped later in the range was never armed. A successful exec left the flag set, so the next image was not armed either.

Fix: remember each armed page. Retry pages that are not mapped yet. Clear that state on successful exec.

## Fix: `fork` killed a child on an armed data page

`data=` sets the range to `PROT_NONE`. `fork` recorded the child tgid and did not copy the tracked-page list. The child inherited the protection. The fault hook did not restore the page, because the child's instruction pointer was not in its own list, and delivered `SIGSEGV`.

TLC trace: Arm, Fork, ChildRead, `dead = TRUE`. On the x86 guest, `/tmp/forkarm` printed `child exit 0` with the module unloaded and `child signal 11` with `path=forkarm data=260000000-260001000`.

Fix: copy the parent's tracked pages and armed-data list to the child. Restore an armed data page even when the faulting instruction is not in the tracked list. `extra forkread` covers this on both arches.

## Fix: A non-matching exec left tracked pages behind

A tracked process that execs a path which does not match keeps its tgid. The old page list was dropped only when the new path matched. The new address space does not contain those pages. An instruction fault at an old address still matched the list. `mprotect` failed, and the hook returned 0, so the fault retried until `SIGALRM`.

Exit deleted the tgid record and left the same list. A reused tgid could attach those pages to the next process.

TLC trace: Track, ExecOther, Jump, `hung = TRUE`. Before the fix, `path=staleexec` exited 139 (`SIGSEGV`) with the module unloaded and 142 (`SIGALRM`) with it loaded.

Fix: drop that tgid's pages on a non-matching exec and on exit. If `mprotect` fails in the fault hook, deliver the signal. `extra stale` must die with `SIGSEGV` (exit 139), not hang.

## Fix: Arming a read-only page made it writable

`pb_handle_data` restored every armed page as `PROT_READ|PROT_WRITE`. A `PROT_READ` page in `data=` was set to `PROT_NONE`, then came back writable after the read fault. A later store succeeded.

TLC trace: Arm, Read, Write, `wrote = TRUE`. On the x86 guest, `/tmp/roarm` exited 3 with the module unloaded (the write faulted) and printed `write 1` with `path=roarm data=260000000-260001000`.

Fix: save the VMA's read/write bits when arming, and restore those bits. `extra roarm` requires the following store to fault. Both full suites passed after this fix.

## Fix: `mremap` left an armed page inaccessible

`data=` sets a page to `PROT_NONE` and records that address. `mremap` moved the mapping and left the record at the old address. A read at the new address was not restored. Outside the `data=` range the fault hook ignored it, so the process died with `SIGSEGV`.

TLC trace: Arm, Move, Read, `dead = TRUE`. On the x86 guest, `/tmp/moveread` printed `moved B` with the module unloaded and exited 3 with `path=moveread data=260000000-260001000`.

Fix: move the armed record when the new address is still in range, and restore the saved protection when it is not. `extra moveread` covers both, with `data=260000000-260001000` and `data=260000000-280000000`.

## Fix: `munmap` left the armed record behind

`data=` records a page and sets it to `PROT_NONE`. `munmap` removed the mapping and left that record. A new mapping at the same address was not armed again, because the next arm attempt skipped an address already on the list. The new bytes were read with no fault and no trace line.

TLC trace: Arm, Unmap, Remap, TryArm, Read, `missed = TRUE`. `/tmp/rearm` printed `trace 1` and exited 2, twice on x86 `6.8.0-101-generic` and twice on arm64 `6.6.62+rpt-rpi-v8`.

Fix: `munmap`, and a replacing `mmap`, drop armed, seen, and tracked entries for that range. `extra rearm` passed twice on each arch, then the full suite once on both.

## Fix: A store into an armed page was not restored

`data=` makes the page inaccessible and the fault hook restores it only on a read. A store is a write fault. The hook delivered `SIGSEGV` even when the saved protection included write.

TLC trace: Arm, Write, `dead = TRUE`. `/tmp/wrarm` exited 3, twice on x86 `6.8.0-101-generic` and twice on arm64 `6.6.62+rpt-rpi-v8`.

Fix: a write fault on an armed page is restored too, but only if the saved protection includes write. A write to a page that was read-only still faults. `extra wrarm` and `extra roarm` passed twice on each arch, then the full suite once on both.

## Fix: Making an armed page executable dumped nothing

`data=` sets the page to `PROT_NONE`. A later `mprotect` to execute dumps the page before that protection is installed. `copy_from_user` fails, so the marker never reaches a dump.

TLC trace: Arm, MprotectX, `missed = TRUE`. `/tmp/noneexec` printed `dump 0` and exited 2, twice on x86 `6.8.0-101-generic` and twice on arm64 `6.6.62+rpt-rpi-v8`.

Fix: if the range is armed, restore a readable protection before the dump. `extra noneexec` passed twice on each arch, then the full suite once on both.

## Fix: `mprotect` left the armed record behind

`data=` records a page and sets it to `PROT_NONE`. A later `mprotect` of that page changed its protection but left the record. The next arm attempt skipped an address already on the list, so the page was never made inaccessible again and nothing was traced.

TLC trace: Arm, MprotectW, TryArm, Read, `missed = TRUE`. `/tmp/disarm` printed `trace 0` and exited 2, twice on x86 `6.8.0-101-generic` and twice on arm64 `6.6.62+rpt-rpi-v8`.

Fix: any `mprotect` drops armed and seen records for that range, so the next arm attempt re-arms a non-executable page. `extra disarm` passed twice on each arch, then the full suite once on both.

## Fix: A forked child could fault before the parent finished the copy

`real_sys_fork` returns in the parent and in the child. The parent's `pb_note_child` copies the tracked pages and armed records into the child tgid, but it runs after the fork has already returned. A child that reads an armed page in that window has no record of its own, so `pb_handle_data` found nothing, returned 0, and the real `SIGSEGV` was delivered. The child died.

Observed once: an x86 suite run reported `forkread: child died`. It did not recur in 30 standalone `forkread` runs, three ordered `read` then `forkread` sequences, or two later full suites on both arches.

Fix: a data fault also consults the parent tgid's armed record and tracked page, which is correct because `fork` shares the page tables. `extra forkrace` runs 200 fork-and-fault children per invocation and is now part of both suites.

What was not shown: `forkrace` passes 200 iterations both with and without the parent fallback, because the test waits for each child, so the parent always wins the lock. The fix rests on the code reading and the one observed failure, not on a reproducing test. If the failure returns, this fallback is the first thing to check.

Modelled in a TLA+ spec kept locally under `drop-loop/models`, listed in `drop-loop/LOOP.md`. With `useParent = FALSE` the fault handler consults only the child tgid and TLC reports the counterexample Fork, ChildFault, `sigdeliv_child = TRUE`, with no copy in between. With `useParent = TRUE` the property holds over the whole state space. That is the evidence the window is real and the fallback closes it.

## Fix: A child's records survived the child's own exit

`pb_note_child` runs in the parent after the fork: `pb_tgid_add`, then `pb_copy_tracking`. The child can run and exit in between. Its `do_exit` drops records that do not exist yet, and the parent then registers a tgid that is already dead and copies pages into it. That tgid stays in the tracking list, so a later process that reuses that pid is treated as a target and inherits stale pages. This is the exit-leak class above, on the child side, and it was introduced by the `fork` fix.

Modelled in a TLA+ spec kept locally under `drop-loop/models`, listed in `drop-loop/LOOP.md`. Property `EventualClear`, with weak fairness on the cleanup so stuttering cannot starve it. `useFix = FALSE` reproduces the shipped order and TLC reports `Temporal property EventualClear was violated` on Fork, TgidAdd, CopyBegin, CopyLand, ChildExit, with the tgid still registered and the records still copied. `useFix = TRUE` satisfies the property.

Fix: do not register a tgid whose task has already exited, and drop the records again if the child died while the copy ran. `pb_child_alive` uses `find_vpid` and `get_pid_task`. Both suites pass, including `extra forkrace` and `extra pair`.

## Fix: Two threads could dump the same data page twice

`pb_handle_data` tested `data_seen`, then ran `dump_to_file` with no lock held, then added the record. The test and the insert were not one critical section, so two threads faulting the same armed page in the same handler epoch could both observe an empty list, both dump, and both write a trace line. That breaks the documented "dumped once per handler epoch" and gives `pb_rank` two index rows for one address.

Modelled in a TLA+ spec kept locally under `drop-loop/models`, listed in `drop-loop/LOOP.md`. TLC reports Seen1, Seen2, Dump1, Dump2, Dump1Done, Dump2Done, with `dumps = 2` and `traces = 2`, violating `Safe`.

Reproduced on x86 `6.8.0-101-generic`: 8 threads released from a barrier onto one armed page produced 2 trace lines in 8 of 8 runs. Four threads produced 1. The count grows with the thread count, which is the signature of a lost update rather than a coincidence.

Fix: `pb_data_claim` tests and inserts under one `marea_lock` hold, and `pb_data_unclaim` releases the claim if the dump then fails, so a later fault can retry. `extra dumprace` requires exactly one trace line from 8 barriered threads. It failed 8 of 8 before the fix and passed 4 of 4 on x86 and 3 of 3 on arm64 after it, with the full suite passing on both.

## Fix: A reader could take a real SIGSEGV while the module was arming or disarming

`data=` deliberately makes a page inaccessible so the fault reveals which handler consumed it. Both the arming and the disarming had a window where the page was `PROT_NONE` with no armed record. `pb_handle_data` found nothing and returned 0, so `fh_force_sig_fault` fell through to the real handler and the process took a signal that the module had caused itself.

Two windows, both in the shipped code:

- Arming: `pb_arm_range` called `pb_mprotect(PROT_NONE)` and only then added the record.
- Disarming: `pb_disarm_range`, reached from any `mprotect` overlapping the range, deleted the record while the page was still `PROT_NONE`, and the real `mprotect` had not run yet.

Modelled in a TLA+ spec kept locally under `drop-loop/models`, listed in `drop-loop/LOOP.md`. The shipped order violates `Safe` with `ProtNoneUnrecorded` then `Read` and `dead = TRUE`. Recording first, `armFirst = TRUE`, holds.

Reproduced on both arches with one thread re-arming in a loop and one thread reading: `SIGSEGV` in 4 of 5 runs on x86 `6.8.0-101-generic` and 4 of 5 on arm64 `6.6.62+rpt-rpi-v8`. As a suite case, `extra armrace` failed 5 of 15 before the fix and 0 of 15 after.

Fix, in three parts:

- `pb_armed_claim` inserts the record under `marea_lock` before the page is made inaccessible, and `pb_armed_unclaim` removes it again if the `mprotect` fails. The record now outlives the protection it explains, in the arm direction.
- `pb_disarm_range` restores each page to its saved protection first and deletes the records in a second pass, so the reverse also never leaves an unowned `PROT_NONE` page.
- `pb_handle_data` is convergent. With no record it asks `pb_page_satisfies` whether the faulting access is already legal, which is what a racing thread's restore or remap leaves behind. Legal means swallow, otherwise deliver the signal. This also stops a fault that was already resolved from turning into a crash.

A note on the count: `armrace` sometimes reports two trace lines and that is correct. The reloader advances the handler epoch on each `mprotect`, and the module promises one dump per handler epoch, so a second epoch legitimately dumps again. The defect is the crash, not the count.

## Fix: Unloading the module stranded pages it had made inaccessible

`data=` works by making a page `PROT_NONE`, and the only thing that can turn it back is this module's own fault handler, running inside the target process. `fh_exit` freed the records and restored nothing, and it could not: `module_exit` runs in the process doing the removal, and `mprotect` only affects the caller's address space. So after `rmmod`, a process holding an armed page took `SIGSEGV` on its next access to that address, a signal the module had caused itself.

Reproduced on x86 `6.8.0-101-generic` with a `mkfifo` gate so the read happens only after the module is confirmed gone: the page is `---p` in `/proc/self/maps` while loaded, `rmmod` returns 0 with `refcnt 0` and `unloaded` in `dmesg`, the page is still `---p`, and the read faults. The target can rescue the page with its own `mprotect`, so this is an unhandled signal, not lost data and not an unrecoverable process. Not reproduced on arm64.

Getting this wrong cost real time. The first several attempts concluded the opposite, that the page was fine after unload, and the reason was the harness: the child did `open()` on a gate file that did not exist yet, so the open failed, the wait was skipped, and the read happened while the module was still loaded, where the module correctly restored the page. Use a FIFO and block on `read()`; a plain file is not a gate. The test must also confirm the module is really gone, with `lsmod` and `dmesg`, before the read.

Fix: while any armed record still describes a page that is `PROT_NONE`, the module holds a reference to itself, so `rmmod` returns `-EBUSY` and the fault handler stays available. Three deliberate choices:

- State is a per-record `restored` flag, not a counter. A counter leaks in two opposite directions: too high and the module is never removable, too low and this stranding bug returns silently. The first version of the work item leaked permanently by leaving the queued flag set when it found a page still inaccessible, so no later release could ever be queued, and clearing the Pi needed a reboot. arm64 caught that on the first run.
- The reference is dropped from a work item, never from a hook. If the last `module_put` ran inside the fault handler, `module_exit` would execute on the fault path, call `pb_remove_hooks`, and free the module text the handler is still running in.
- The pin is taken before `PROT_NONE` is set, so there is never an instant where a page is inaccessible and the module is removable.

Modelled under `drop-loop/models/module-pin`: `hookdrop` violates `NoStrand`, `leak` violates `NoLeak`, and the shipped configuration holds both. `extra pin` asserts `rmmod` is refused while a page is held and `extra pinoff` asserts it is permitted after a read. Both suites pass on x86 and arm64.

One accepted cost: the release is asynchronous, so `rmmod` can be refused for a moment after the last armed page has gone. Scripts that remove the module immediately after a target exits may need to retry. That is the price of not dropping the reference from a hook.

Unresolved, recorded in cycle 5 and not a confirmed defect. The bullet above says the pin is taken before `PROT_NONE` is set. The tree does not do that: `try_module_get` appears once, in `pb_pin_update_locked`, and every call site of that function is a release path (`pb_disarm_range`, `pb_drop_data_state`, `pb_drop_user_range`, `pb_armed_unclaim`, `pb_armed_after_move`, `pb_release_armed`, `pb_handle_data`). `pb_armed_claim`, the arming path, does not call it. Measured on x86 `6.8.0-101-generic`, ftrace, `path=condc data=260000000-261000000`: `/proc/modules` reads 0 while an unrestored record is on `data_armed`, for the whole run. That is consistent with the code and not with the bullet. Against it, `extra pin` passes on x86 and arm64 and it gates on `rmmod` being **refused** while a page is held, so a reference is held in that window. Both facts are recorded; neither has been reconciled, and the refcount is not a usable witness either way. A store into the page is the witness that a record exists.

## Fix: `mremap` moved an armed page into a window with no record

`fh_sys_mremap` called `real_sys_mremap` first, so the kernel moved the page while it was still `PROT_NONE`, and only afterwards did `pb_note_mremap` move the armed record. In between, the page sat at its new address, inaccessible, with the record still filed under the old one. `pb_handle_data` found nothing, and the reader took a real `SIGSEGV`.

The settle step had the mirror-image defect: for a destination outside the armed range it deleted the record and only then restored the protection, so it also left an inaccessible page with no record.

Modelled in a TLA+ spec kept locally under `drop-loop/models`, listed in `drop-loop/LOOP.md`. The shipped order violates `Safe` with `MovePage` then `Read` and `dead = TRUE`; moving the record first, `moveRecordFirst = TRUE`, holds.

Reproduced with a reader spinning on a destination that is kept mapped by a shadow page, so a fault there can only be the module's. 8 of 8 failures on x86, and the control without the module survived 3 of 3.

Fix, in three parts:

- A page we armed is ours wherever it now lives, so `pb_handle_data` consults the record before the range test. A moved page can legitimately sit outside `data=`, and the record is what says it is ours.
- `MREMAP_FIXED` names the destination before the syscall. A page whose destination stays in range has its record relocated ahead of the move, and moved back if the syscall fails. A page whose destination leaves the range is released by `pb_release_armed`, which restores the protection and only then drops the record, so it arrives accessible and needs no record.
- The same restore-before-forget order as `pb_disarm_range`.

`extra mremaprace` covers it. It failed 8 of 8 before the fix and 0 of 25 after, with both suites passing on x86 and arm64.

Still open, and it needs its own test: `mremap` without `MREMAP_FIXED` still has the window. The kernel picks the destination, so the record cannot be placed ahead of the move. Only the record can be consulted afterwards, which is too late for a reader that already faulted. It is recorded under the next heading, where it is not counted as a confirmed defect because no reproduction was found.

## Not a defect: Note on the `MREMAP_MAYMOVE` window above

The entry above calls the non-`FIXED` window open. That is right about the ordering and wrong about how often it can bite, and the difference is worth recording.

Measured on 6.8.0-101-generic: a same-size `MREMAP_MAYMOVE` does not move anything. Every page tested came back at its original address, so the record was never misplaced and there is no window at all. A move only happens when the size changes and the neighbouring pages are occupied; that case does relocate, into the mmap area.

So no crash was reproduced. Two attempts failed and both are recorded rather than quietly dropped. Forcing a relocation and scanning the whole mmap region from a second thread, with a signal handler that tells a module-caused fault apart from a fault on a plain unmapped address, produced no failure with or without the module. The window is real in the ordering but too narrow to hit from user space.

Hardening, not a bug fix: when `MREMAP_FIXED` is absent and `old_len != new_len`, the armed pages are released before the syscall, so they arrive accessible and need no record. The same-size case is left alone, because releasing there would drop arming for a call that does not move anything. The size-change guard is empirical, taken from the measurement above on this kernel; a kernel that relocates on a same-size move would need the guard widened. The cost when it does fire is that a relocated page is not re-armed until the next executable `mprotect`. Both suites pass on x86 and arm64.

Do not count this as a confirmed bug. It has no reproduction.

A third attempt failed too, and the reason is worth keeping because it closes the question rather than leaving it open. The reader has to be sitting on the destination at the moment the window opens, and the destination is never knowable in advance:

- A sweep is useless. It spends its time faulting over addresses nothing is mapped at, while all the moves complete in microseconds, so it never overlaps the window.
- The destinations look like they step down by a constant stride, so predicting the next one looks attractive. It is not reliable: the gap varies, and a prediction check caught the kernel choosing a different address at the third move.
- Hammering the recently used destinations fails because the kernel always places the next one at a new, lower address, never a repeat. No previously used address is ever the next destination.

With the hardening deliberately disabled, the test still reported zero hits. So on this kernel the window is below what a user space test can reach. That is a stronger statement than "we failed to find a test", and it means the honest conclusion is that the hardening is unfalsifiable by test here rather than merely untested.

What replaced the missing test is a check of the assumption the guard actually rests on. `extra maymove` now asserts that a same-size `MREMAP_MAYMOVE` does not relocate, and fails with a clear message if it ever does, because that is exactly the condition under which `fh_sys_mremap` stops releasing pages and the window reopens. It passes on x86 and arm64. The guard is now tied to a checked premise rather than to a comment.

## Fix: `mremap(MREMAP_FIXED)` returned `EFAULT` over an armed range

`fh_sys_mremap` settled every page ahead of an `MREMAP_FIXED` move. A page whose destination fell outside `data=` was settled with `pb_release_armed`, which is an `mprotect` on one page of the source range. That made the source range non-uniform, and 6.8 `mremap` refuses a non-uniform source range, so the module made the target's own syscall fail. The move the target would get with the module unloaded did not happen. This is a correctness defect, not a missing dump.

The mechanism was confirmed against the kernel, not assumed. ## Fix: an `mprotect` over the armed range removed the `PROT_NONE` it had just installed

## Fix: an `mprotect` naming a strict subset of an armed run leaves the range non-uniform

### The fix

`pb_disarm_range` is deleted. The settle moved to the **after** side of both protect hooks, so it has one: `fh_sys_mprotect` (`pagedrop.c:1148`) and `fh_sys_pkey_mprotect` (`pagedrop.c:1183`) call the kernel first, then `if (!ret) pb_armed_rearm(current->tgid, addr, len)` (`pagedrop.c:1162` and `pagedrop.c:1186`), then the cycle-5 `pb_try_arm(addr, end, true)`. `pb_armed_rearm` (`pagedrop.c:925`) walks the pages the call named, and for each one that still has an armed record it re-reads the protection the kernel actually installed through `pb_can_arm(page, &prot, true)`, installs `PROT_NONE` again, sets `entry->prot = prot` and `entry->restored = false`, and forgets the page's `data_seen` rows via `pb_seen_forget` (`pagedrop.c:865`). A page the `mprotect` left `PROT_NONE`, or one that is gone, cannot be armed and its record goes with it through `pb_armed_forget` (`pagedrop.c:884`), which sets `restored = true` before dropping it.

The run therefore comes back as one uniform `PROT_NONE` mapping with every named page re-armed at the same protection, so the target's own `MREMAP_FIXED` over the run is not refused. No dump is lost: `pb_seen_forget` runs on both the re-arm and the forget path, so a page's next read still dumps again even at the same handler epoch.

The asymmetry that made this site fixable and the read entry above not: the read path has no "after the syscall" side to move the bookkeeping to. Here the kernel rewrites the very pages the split is about, so settling after the syscall reads the real protection instead of a stale one.

Adversary, x86 `6.8.0-101-generic`, ftrace, `adv6`: `mprotect(DATA_LO+4096, 3 * PAGE, PROT_READ)` over a 3-page mapping returns **0**, not `-ENOMEM`, and applies to the mapped prefix only — `MAP 260000000-260001000 rw-p`, `MAP 260001000-260003000 r--p`, and the target's own move is then refused. So the part that would fail is the tail past the mapping, which names no armed page, and the kernel reports success.

Red team, x86 `6.8.0-101-generic`, two runs each construction: with a `MAP_SHARED` page from an `O_RDONLY` file inside the range, `PROT_READ|PROT_WRITE|PROT_EXEC` leaves the range `---p` again, **one VMA**, `POST distinct=1`, and the move succeeds — consistent with the cycle-5 reorder, since `pb_try_arm` runs after the syscall with `allow_exec` and re-arms. `PROT_READ|PROT_WRITE` leaves the range `rw-p`, one VMA, move succeeds — but the unloaded control shows the **kernel** had already written `rw-p` to the first two pages before returning `ENOMEM`, so that construction does not isolate `pb_disarm_range` at all.

So `mprotect` on this kernel is **not atomic**: it applies protection to the leading pages of a range before it can fail. No bounded-length, non-atomically-failing `mprotect` over a multi-page armed range was found. Recorded as a limit of the measurement, not a claim that the code is safe: if such an `mprotect` exists, the split it would leave is the same one the entry above already documents for the success branch.

**Cycle 7, model only.** `drop-loop/models/mprotect-subset/failafter-partial.cfg` violates `Safe` and `FailedCallKeepsArm`: the after side is gated on success (`if (!ret)` at `pagedrop.c:1161`), so a partially-applied failed `mprotect` gets no settle at all, and the leading page the kernel already rewrote is the one the run ends up split on. `failafter-clean.cfg` holds, which is consistent with the finding above: with the kernel installing nothing, there is nothing to split. **No kernel was run** and the spec engineer did not measure whether 6.8 can be made to fail in the armed range at all, so the entry stays `Not a defect` — the branch remains unconstructed on a kernel, and the cycle-7 fix does not cover it if it is ever reached. `pb_disarm_range`, named above, no longer exists; the sentence describes the cycle-6 tree.

## Fix: Holding `marea_lock` across `mprotect` deadlocked against the mmap hook

Two paths took the two locks in opposite orders.

- `fh_vm_mmap_pgoff` is an internal kernel hook. The kernel calls it with `mmap_write_lock` already held, and the hook calls `pb_drop_user_range`, which takes `marea_lock`. So `mmap_write_lock` is held while `marea_lock` is wanted.
- `pb_disarm_range`, `pb_armed_after_move` and `pb_release_armed` held `marea_lock` across `pb_mprotect`, which reaches the real mprotect and wants `mmap_write_lock`. So `marea_lock` was held while `mmap_write_lock` was wanted.

That is ABBA. One thread in the restore path and one thread in a plain `mmap` deadlocks, with the two locks held and both waits outstanding.

Modelled in a TLA+ spec kept locally under `drop-loop/models`, listed in `drop-loop/LOOP.md`. `heldLock = FALSE`, the shipped nesting, violates `Safe` with A holding `marea` waiting for `mmap` and B holding `mmap` waiting for `marea`. `heldLock = TRUE` holds.

The suite did not catch this. No case in 47 deadlocked, because the interleaving needs one thread restoring while another maps.

Fix: no path holds `marea_lock` across `pb_mprotect` any more. Each of the three collects the record under the lock, restores with the lock released, then drops the record. The record still outlives the restore, so a reader that faults in that gap finds one and is handled, and a restore that lands on a page a reader already fixed is the same protection. Both suites pass.

## Fix: `MREMAP_DONTUNMAP` left an armed source inaccessible for good

`fh_sys_mremap` did not know `MREMAP_DONTUNMAP`. With that flag the kernel moves
the pages and **keeps the source VMA**, with its protection. The move path
relocates the armed record to the destination, so an armed source was left
`PROT_NONE` with no record left to restore it, and every later access to the
source was a `SIGSEGV` this module caused. The flag also breaks the premise
`extra maymove` checks, that a same-size move does not relocate: `MREMAP_DONTUNMAP`
always moves, even at the same size, so the size test below cannot cover it.

Measured on x86 `6.8.0-101-generic`, ftrace, `data=260000000-260001000`, with
the branch disabled: `dontunmap: fault on the source`, and the same binary with
the branch in place reads the source and the moved page cleanly. The case reads
the **source** after the move specifically, because that is where the stranding
was.

Fix: on `MREMAP_DONTUNMAP` every armed source page is released before the
syscall, as for a resizing move. Both ends arrive accessible and the moved page
is armed again by the next executable `mprotect`. `MREMAP_DONTUNMAP` is defined
under `#ifndef`, since the flag arrived in 5.7 and is absent from some header
sets this file builds against.

With `MREMAP_FIXED` as well, both release loops run. That is a valid call when
the size does not change: the kernel unmaps the destination and keeps the
source. If it rejects the call instead, for a size change or an overlap, the
pages released here are merely accessible and the next executable `mprotect`
arms them again.

New cases `extra dontunmap` and, from upstream, the same geometry wired into
both runners.

## Fix: a `comm` containing a space or a newline could forge an index row

`/tmp/pagedrop.index` is one row per dump, `%d %s %lx %lu %s\n`, and the name
field came straight from `current->comm`, which is whatever the target chose.
A newline in it ends the row early and the rest of the name is read as fields,
so a target can write index rows for dumps that never happened. A space does
the same to the column count, so every tool that splits the index on
whitespace mis-parses the row.

Measured on x86 `6.8.0-101-generic`, ftrace, with the sanitiser bypassed and
`prctl(PR_SET_NAME, "ex tra\nx")`, the index really did contain a forged row:

```
3336 extra 7967816d96a000 0 mmap
...
3336 ex tra
x 7967816e5000 443 mprotect
```

Two rows had the wrong field count. With the fix the name arrives as
`ex_tra_x`, there is exactly one row for that dump, and every line in the index
has five fields.

Fix: `pb_index_comm` replaces every byte at or below a space, and `0x7f`, with
an underscore, and substitutes `-` for an empty name. It writes in place
because `comm` is the current task's own buffer.

New case `extra commname` plus an `index commname` check in both runners, which
asserts the sanitised name is present **and** that no line in the index has a
field count other than five. The field-count assertion is the part that would
have caught this; the name assertion alone would not, because the forged row
also carries `ex tra` somewhere in it.

## Fix: a process killed by `SIGSEGV` left its armed records, and the pin was never released

Found 2026-10-06 while porting upstream's fixes, and it was blocking measurement
of everything else.

While any armed record describes a page the module made `PROT_NONE`, the module
holds a reference to itself. That is correct, and it was verified working: live
processes holding armed pages pin the module and `rmmod` is refused. The defect
was what happened when the process **died**. A `SIGSEGV` in `extra` left
`rmmod: ERROR: Module pagedrop is in use` with `/sys/module/pagedrop/refcnt` at
1, and after every `extra` process was gone `rmmod` was still refused. The
records outlived the process, so `pb_pin_needed_locked()` stayed true and the
release work item never fired.

With the retrying `unload()` in the runners, a case that left this state stopped
the run instead of continuing against a pinned module. Before that hardening the
suite carried on and every later case measured the previous build, which is how
this stayed invisible.

Fix: the fork cluster. `pb_note_child` now takes a task reference with
`find_get_pid()` and holds it across both liveness checks, keys the child on
`task_tgid_nr()` rather than the pid the fork returned, and judges liveness with
`pb_group_alive()`, which reads `task->signal->live` instead of one task's
`PF_EXITING`. Checking a single task is wrong for a thread group, so two threads
could each judge the other already gone and both skip the cleanup, and a child
keyed on a namespace-local pid kept records nothing would ever drop. `struct
pb_tgid` gained an `own` flag, set for a matched name or exec and cleared for a
fork, so a parent still inside its own copy is walked past by
`pb_records_tgid()`; the copy and the ownership flip happen in one
`marea_lock` hold so a thread cannot observe a half-copied child.

Verified after the port, x86 `6.8.0-101-generic`, `mremaprace` standalone with
the segfaulting target and the suite's own `data=` range: **`rmmod` released on
every run**, six of six, module gone afterwards. The stranding is gone.

Consequence for the suite: the `mremaprace` entry above no longer stops a run, so
the suites complete again.

## Fix: A data page read through a second handler version is not traced again

The contract is one dump per handler epoch. A read fault restores the page and
keeps its armed record, so the page never faults again and the address was observed
once for the life of the process.

**The key, which is the whole fix.** `pb_ip_tracked` already knows which tracked
page the faulting instruction was in, so that page is stored in the `data_seen`
row, and a dump of that handler page re-arms exactly the addresses that version
consumed. The key is the **handler page**, not the global `epoch` counter: the
counter advances on every dump of any page, so keying on it re-arms every stale
row, and each re-arm buys another fault and another dump. An attempt that did so
produced **177,256** read rows in one `dumprace` run and regressed four cases.
The hook also skips `why=read`, so a data page cannot trigger the re-arm that
follows its own dump. Rows are dropped under `marea_lock` and re-armed with it
released, because `pb_armed_rearm` calls `pb_mprotect`.

### New case `extra epochread`, with the bound the first attempt needed

Read a data page, re-`mprotect` the handler page so its version changes, read the
same address again. Two trace lines expected; one means the defect is back.

It also bounds the work: it fails if the second handler version added more than 16
index rows. That bound is a **delta**, not an absolute count — a plain run already
writes about 450 rows for the process's own executable pages, so an absolute bound
has to sit above the baseline and stops being a check. Measured cost: **2 rows**.
Verified live rather than assumed: forced to 0, the case fails with "the second
handler version added 2 index rows".

**Not claimed.** The 177,256-row flood could not be reproduced from any
configuration afterwards, including a reconstruction of the original hook; that
build also produced 449 rows. So the ceiling is a guard whose triggering threshold
has not been observed. What is shown is that it is live code and that the shipped
key adds 2 rows where the original added one per tracked page.

A/B, both arches, two runs per leg, counting trace lines for the data address:
with the re-arm **2** and `epochread ok`; with the hook disabled **1** and a
failure. x86 `6.8.0-101-generic` ftrace, arm64 `6.6.62+rpt-rpi-v8` kprobe. Suites
after it: x86 **65 PASS / 0 FAIL** twice, arm64 **67 PASS / 0 FAIL**, `upx-ok 1`,
module unloaded. `dumprace` 447 index rows on x86 with one trace line; `armrace`
2,468 rows.

**The cost, stated plainly:** one fault per data page per handler version instead
of once per page. `data_seen` is now keyed by the consuming handler page as well
as the tgid, which erodes the "no per-thread view" limit in `AGENTS.md`; the
limit itself is not gone, since the key is still per tgid.

## Superseded: A data page is only ever traced once, not once per handler epoch

**Fixed.** See "A data page read through a second handler version is not traced again"
below for the fix, its A/B on both arches and its cost. The text after that note is
kept as the record of the defect, including the `drop-loop/models/epoch-rearm`
configs and the cycle-5 decision not to fix it.

Not a crash, and not fixed. The contract in `README.md` and in the fix for "a data read was logged on every fault" says one dump per handler epoch. The code does one per data page, for the life of the process.

A read fault restores the page but leaves the armed record in place, so `pb_arm_range` skips it for ever. The page stays readable, no later read faults, the hook is never entered, and no trace line is written at any later epoch. Only a `munmap`, a replacing `mmap` or an `mprotect` over the data page clears the record.

**Cycle 7 narrowed this, so the old wording is no longer exact.** `pb_armed_rearm` (`pagedrop.c:925`) now runs on **every** successful `mprotect` that names an armed page, not only exec and wx ones, and it both re-installs `PROT_NONE` and calls `pb_seen_forget` (`pagedrop.c:865`). So an explicit `mprotect` over an armed data page now **re-arms** it and lets its next read dump again, at the same handler epoch as the last one. The measurement above — one trace line, not two, when only the code page is re-`mprotect`ed — was not re-run after the fix and this entry does not claim it still holds. Two consequences, one of them a finding nobody measured: the per-epoch dedup is now restated from every read to every read *and* every successful `mprotect`, and because `dump_to_file` names the file `/tmp/<page>_<epoch>`, a re-armed page read again at the **same** epoch writes that file a second time, so the second generation overwrites the first while the index gains a second `why=read` row. That was flagged by the cycle-7 red team as an observation and **was not measured**.

Measured on x86 `6.8.0-101-generic`: arm, read once, re-`mprotect` the code page so it is dumped again and its epoch advances, read the same address. One trace line, not two. Clean trace and module unloaded, zero lines.

Modelled in a TLA+ spec kept locally under `drop-loop/models`, listed in `drop-loop/LOOP.md`. The shipped behaviour violates the property on Arm, Read, AdvanceEpoch, ReadStale; re-arming on epoch change holds.

Left unfixed on purpose. Re-arming a stale record costs a fault per bytecode read rather than one per page, and every re-arm reintroduces the arming-window class of bug that caused the earlier `SIGSEGV` fixes. The decision and the options are documented in `AGENTS.md`.

## Fix: a child that inherited its parent's `comm` claimed ownership of records it never had

Found 2026-10-06 while porting upstream's fork-ownership fixes, and it was the
last thing between this tree and a green suite on both arches. `extra
vforkfork` and `extra vforkwrite` failed on x86 and arm64 alike.

`pb_is_target` decides whether a process belongs to the trace and, if it does,
whether it *owns* its records. `pb_copy_tracking` gives a new child a copy of
its parent's lists and only then sets the child owning. Between those two
moments the child must resolve records through the parent, which is what the
`use_parent` walk in `pb_handle_data`, `pb_ip_tracked` and `pb_take_page` is
for. `use_parent` is derived as `!pb_tgid_own(tgid)`, so it is decided by
*ownership*, not by whether a record was actually found.

This tree tested `pb_name_matches()` first and registered the match as owning.
A child inherits its parent's `comm`, so the child of a tracked target matches
`path=` while holding none of the parent's records. It was therefore marked an
owner, `use_parent` was false, the ancestor walk never ran, no record was
found, and the armed page was never restored. The read fault fell through to
`pb_page_satisfies`, which correctly refuses to swallow a genuinely illegal
access, so the process took a `SIGSEGV` the module had caused.

Upstream tests the tracked parent first and only then the name:

```
parent = pb_parent_tracked();
if (parent || pb_name_matches(current->comm)) {
	pb_tgid_add(tgid, !parent);
	return true;
}
```

so a child of a tracked parent is registered non-owning whatever its name says,
and `pb_copy_tracking` still promotes it to owner once the copy exists. The
ordering is the whole fix; `pb_parent_tracked` itself was already identical.

This is a second-generation case, which is why the suite caught it and reading
the code did not. `vforkfork` faults in a grandchild produced by a raw
`SYS_clone` inside a `vfork`ed child, two `fork`-like edges below the process
that owns the record. A single-generation port looked correct throughout.

Isolated with a 40-line reproduction kept outside the suite: one process maps
`data=`'s page `rw-p`, maps a second page and `mprotect`s it `r-xp`, `vfork`s,
the child `munmap`s an unrelated address, the child makes a grandchild with a
raw `SYS_clone`, and the grandchild reads the armed page. Both modules leave
that page `---p` and both arm it identically, so arming is not the difference;
upstream's grandchild reads the byte, ours takes `SIGSEGV`. That repro was
also the evidence that ruled out three other suspects, all of which had been
changed or reverted before it existed: the `pb_armed_run` restore in
`pb_handle_data`, the `exec_ok` argument on the fault-path `pb_try_arm`, and a
`tgid` reassignment in `pb_handle_data` that was tried and reverted because
nothing measured it.

Measurement, one hunk, both arches, two runs each direction:

| | `vforkfork` | `vforkwrite` |
|---|---|---|
| x86 `6.8.0-101-generic`, hunk reverse-patched | grandchild killed by signal 11, 2/2 | child status `0x8b`, 2/2 |
| x86, fixed | `vforkfork ok`, 3/3 | `vforkwrite ok`, 3/3 |
| x86, module unloaded | `vforkfork ok` | `vforkwrite ok` |
| arm64 `6.6.62+rpt-rpi-v8`, hunk reverse-patched | grandchild killed by signal 11, 2/2 | child status `0xb`, 2/2 |
| arm64, fixed | `vforkfork ok`, 2/2 | `vforkwrite ok`, 2/2 |
| arm64, module unloaded | `vforkfork ok` | `vforkwrite ok` |

arm64 `vermagic 6.6.62+rpt-rpi-v8`, built on the Pi, `upx 5.0.2`. Full suites
after the fix, `upx-ok 1` present in both and the module unloaded at the end
of each: x86 **64 PASS / 0 FAIL**, `ALL PASS`, exit 0, twice; arm64 **66 PASS /
0 FAIL**, `ALL PASS`, exit 0, once. `mremaprace` did not fire in either x86
run. arm64's `armexec` is green too, on the fixed test stub.

Not committed. A clone should apply this by hand from the description above;
the hunk is the ordering of three lines in `pb_is_target`.

## Fix: the runners' dump cleanup dies on a large dump count and silently measures stale state

Both runners cleaned with `sudo rm -f /tmp/[0-9a-f]*_[0-9]*`, in **110 places**.
The shell expands that glob into the argument vector, so at a large file count the
exec itself fails and **nothing is removed**, and because there is no `set -e` the
failure is only visible as a `sudo: Argument list too long` line among the output.

The consequence is worse than a slow run. Each case cleans, creates its own dumps,
then a checker looks for what *it* created. With cleanup dead, every case sees the
previous case's files, so the suite reports failures that have nothing to do with
the code under test. On a **committed, unmodified** tree after a run had left about
180,000 files behind: `simple`, `capture mremap`, `exact`, `dumprace` and
`fixedwx` all failed, `RC=1`, on a tree that had just passed 64/0. Anyone reading
only the FAIL lines would have concluded a regression.

Demonstration on the x86 guest, recreating the count:

```
created: 200000 files
OLD glob:    rm: Argument list too long
files surviving the old glob: 200000
NEW find -delete:
files surviving find -delete: 0
```

The old form removes **none** of them. Fix: both runners gained a `clean_dumps`
helper using `find /tmp -maxdepth 1 -name '[0-9a-f]*_[0-9]*' -type f -delete`,
which walks the directory and passes one path at a time, and all 110 call sites
now use it. The two cases that also removed `/tmp/pbpin.fifo` pass it through as
an argument.

The pattern keeps the original trailing `_[0-9]*`. A first version dropped it and
matched any file starting `a`-`f` and containing an underscore, which deleted the
test binaries themselves. Worth keeping in mind when widening a pattern.

A defect in the harness, not in the module, and worth keeping separate from the
flood it followed: the count is reachable from a real target that dumps heavily.

## Fix: a fault the kernel had given up on was turned into a crash

Isolated by instrumenting every path in `fh_force_sig_fault` that hands the fault
back to the kernel, one probe per decline site, and running the suite's own
`mremaprace` geometry until the fatal one fired. It fired on run 33 of 400:

```

```

Three facts in one line. The fault is at `MOVE_ALT`. It was **declined by
`pb_take_page`**, which is reached when the data path did not handle it, and
`pb_take_page` only knows tracked *exec* pages, which `MOVE_ALT` is not. And
`vma=1`: **the page was readable.** A fault on a page the module had no business

the module looked.

That is the convergence rule this file already states for data faults, missing
from the tracked-page path. Fix: before declining, if this is not an instruction

## Left unfixed: the fault-path swallow is a fixed point, not a convergence (model only, never measured on a kernel)

The entry above reasons that returning 0 lets the instruction retry and the retry
is absorbed if the fault was already resolved. The model says that is incomplete,
and the correction matters.

**There are two swallow sites, not one.** `pb_handle_data` had a convergence
branch all along; the fix above added a second. TLC names the site, and
`shipped.cfg` (both gates as shipped) violates at **site A**, `pb_handle_data`,
not at the new one.

**The retry is a fixed point.** A fault the kernel refuses changes no input the
module reads — VMA flags, the armed list, `fault_code`, `error_code` are all
unchanged — so the hook takes the same branch and the target spins. Not
hypothetical: the instruction case did exactly this before the guard went in. The
guard closed the *instruction* instance; whether a **data** instance exists is the
open question.

**Then it is not reachable from a target, on this kernel.** Five constructions,
x86, unprivileged, no module — two `userfaultfd` anon-private MISSING cases, two
shmem MISSING cases, and a shared file truncated under the reader:

```
uffd anon-private MISSING : exited 0 (fallback: no fault), exited 0
uffd shmem MISSING        : exited 85 ('U' = read succeeded), exited 85
shared file truncated     : signal 7 (SIGBUS)
```

No construction produced `SIGSEGV` on a VMA that permits the access. The
file-backed refusals arrive as `SIGBUS`, which `fh_force_sig_fault` passes through
at the `sig != SIGSEGV` test, and `userfaultfd` MISSING falls back rather than
refusing. So the model says the hazard exists *in the code* and the kernel says
the state is not reachable *from user space here*. Both are true; they are about
different things. That moves this from live to latent, which is why it stays open
rather than becoming a declared limit.

Modelled in `drop-loop/models/fault-signal`, five configs, `check_models.sh` ->
`ALL MODELS OK (55 checks)`, 50 before. No kernel run, no `insmod`. `refused` is
the one bit the module cannot read; the model leaves it free, so `fixed.cfg` holds
only under an `ArmedResolvable` assumption and `noresolve.cfg` is registered to
violate on purpose so the suite cannot pass by assuming it away.

**What the loop got wrong here, which is the more useful half.** A loop role tried
to close the residual by requiring an armed record before swallowing. That is a
**regression**, and the suite could not see it: `mremaprace` went from 0/400 to
6/400 while the full suite still printed `65 PASS / 0 FAIL`, because the case runs
once and its rate is about 1.5%. The `mremaprace` fault is precisely a fault with
no armed record, so the gate turned the check off for exactly the case it was
added to fix. Reverted, re-verified 0/400.

## Superseded: `mremaprace` segfaults the target when the wider arm and the wider restore are both present

**Resolved** by "a fault the kernel had given up on was turned into a crash"
above. Kept as a stub because the reasoning here was wrong in a way worth not
repeating.

What it claimed: the target segfaulted because the cycle-5 wider arm and the
